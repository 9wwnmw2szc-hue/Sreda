# Приём заявок: серверная настройка и Telegram

## Реализовано
Настройка хранится в lead_setup по внутреннему business_id: version/step/channels/fields и revision.
GET разрешён активным участникам; POST только owner/admin, с Origin, лимитом и проверкой revision.
Конфликт двух вкладок возвращает 409 без перезаписи. Порядок полей канонический, имя обязательно.
Мастер загружает настройку с сервера и сохраняет каждый переход/изменение. Демо использует прежний localStorage.
Изменение настройки удаляет runtime и незавершённые диалоги/очередь, но не сохранённые заявки.
Для продолжения нужен явный повторный запуск. VK можно выбрать в черновике, но запуск сейчас только Telegram.

Dashboard читает серверные состояния. active требует готового черновика, единственной площадки Telegram,
проверенного токена, runtime.ready, включённого TELEGRAM_WEBHOOKS_ENABLED и свежего heartbeat worker (<60 секунд).
Нет обработчика или постоянная ошибка — paused с пояснением; незавершённая настройка — setup_required.
Остальные решения unavailable. Проверенный токен означает только подтверждение Telegram getMe.

## Подключение
Токен вводится в существующем разделе Подключения, проверяется getMe и шифруется AES-GCM.
Замена/отключение токена сбрасывает runtime. Operator может читать безопасные сведения подключения для Dashboard,
но не изменяет подключение. Токены не возвращаются API.
POST /api/v1/businesses/{id}/telegram/start доступен owner/admin после подготовки конфигурации.
Он регистрирует setWebhook с allowed_updates=[message], max_connections=1 и HMAC секретом, привязанным
к connection_id и generation. drop_pending_updates не включается. Повторный запуск меняет секрет.
Действие Telegram и транзакция PostgreSQL не атомарны: при ошибке предыдущий runtime помечается error,
сценарий нужно запустить заново. При недоступной БД регистрация тоже требует проверки и повтора.

## Приём сообщений
POST /api/telegram/{connectionId} ограничен 64 КБ и проверяет X-Telegram-Bot-Api-Secret-Token.
Привязка к бизнесу берётся из базы, не из тела события. Только личные текстовые сообщения от самого chat owner.
Группы, боты и неподдерживаемые типы сообщений игнорируются. /start начинает анкету, /cancel отменяет,
/skip пропускает необязательное поле. Условные вопросы и вложения пока не поддерживаются.
Начатый диалог сохраняет свой набор вопросов. Ответы ограничены по длине, данные не интерпретируются как HTML.
Диалог истекает через 24 часа. Устаревшие update_id внутри диалога игнорируются.
Событие, продвижение диалога, заявка и ответ в outbox фиксируются одной транзакцией под блокировкой бизнеса.
Повторная доставка события не создаёт вторую заявку. Lead.external_event_id содержит bot ID и update ID.

## Отправка ответов
Отдельный scripts/telegram-worker.mts отправляет постоянную очередь. Порядок внутри одного чата сохраняется.
Транзакция берёт блокировку бизнеса до очереди; сеть ограничена 5 секундами. Один медленный бот может
задержать свой бизнес, не все бизнесы. Для первого пилота используется один worker.
Повторы с задержкой, учитывается retry_after Telegram, максимум 8 попыток; постоянная ошибка приостанавливает runtime.
Исключение: HTTP 403 при sendMessage отменяет только очередь и незавершённый диалог получателя.
Другие чаты продолжают работать, уже принятые заявки сохраняются. Неотправленные ответы не помечаются доставленными.
После исправления токена/сети владелец повторно запускает сценарий. Старые незавершённые диалоги при этом сбрасываются.
Telegram sendMessage не имеет нашей гарантии exactly-once: при потере ответа или сбое DB commit после отправки
клиент может получить повторное сообщение. При этом сохранённая заявка не дублируется.
После успешной отправки текст outbox очищается; отправленные записи удаляются через сутки, update ID через 7 дней.
Неуспешная очередь удаляется при перенастройке; перед реальным пилотом нужно утвердить сроки хранения всех клиентских данных.

## Границы
Это сценарий Приёма заявок на общем подключении бизнеса. Второго бота для этого решения не создаём.
Диспетчер будущих решений, бесплатная переписка с администратором, VK, платежи, PIN и личный вход по коду
не реализуются этим изменением. Ни цена в каталоге, ни active не подтверждают оплаченную подписку.
Денег код не списывает. Использовать только закрытый пилот до реализации правил доступа по подписке.

## Проверки и открытая приёмка
Сервисные тесты проверяют разделение бизнесов/чатов, права, ревизии, ошибочные данные, поддельный webhook,
повторы/конкурентную доставку, откат заявки вместе с событием и outbox, retry_after и порядок сообщений,
постоянные ошибки, остановку worker, неопределённую регистрацию и отключение токена.
HTTPS проверяет реальные routes настройки/состояний и выключенный Telegram по умолчанию.
Telegram transport в тестах подменён; ни один реальный токен не использован.
Браузерная проверка текущего UI открыта из-за ERR_BLOCKED_BY_CLIENT. Реальный Telegram и сеть Яндекса
обязательно проверить после создания окружения; тестовые ответы провайдера не доказывают доступность его API.
