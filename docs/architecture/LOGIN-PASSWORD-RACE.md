# Вход одновременно со сменой пароля

## Проблема
Better Auth username сначала читает хеш и проверяет пароль, затем создаёт сессию.
В промежутке восстановление/смена могут заменить пароль и удалить все прежние сессии.
Без дополнительной проверки запоздалый вход создавал новую действующую сессию по старому паролю.

## Решение
До вызова библиотеки HTTP-обработчик читает userId и текущий credential hash.
После успешного входа, до передачи cookie браузеру, транзакция берёт FOR UPDATE на строку пользователя:
- проверяет, что credential hash совпадает со снимком;
- проверяет наличие именно выданной сессии у этого пользователя;
- при несовпадении удаляет именно эту сессию и фиксирует удаление, затем возвращает обычную ошибку входа без cookie.
Смена и восстановление пароля используют ту же блокировку. Поэтому:
- reset/change первым: финальная проверка отклоняет запоздалый вход;
- финальная проверка первой: reset/change затем удаляет его сессию.
Проверка пароля и выдача подписанной cookie остаются в Better Auth. Внешний API по-прежнему возвращает только ok.
Хеш и внутренний токен используются только на сервере; не попадают в ответы, документацию с данными или логи.
Снимок хеша служит маркером изменения: стандартный hashPassword генерирует новый случайный salt даже для того же пароля.
Отдельная миграция не нужна: token уже есть в таблице session, уточнён только TypeScript-тип.

## Проверки
Тесты используют реальную Better Auth с её поддерживаемым password.verify и стандартным verifyPassword.
Барьер останавливает вход сразу после успешной проверки старого пароля, затем выполняется смена или восстановление,
после чего библиотеке разрешено создать сеанс. Ожидаются AUTH_FAILED, отсутствие Set-Cookie и отсутствие запоздалого сеанса.
Другой пользователь продолжает работать, вход новым паролем успешен. Проверен обратный порядок: сначала вход, потом reset.
На исходном обработчике оба теста воспроизводят ошибку (200 вместо 400); с исправлением проходят.
Эти сценарии работают на PGlite и на PostgreSQL в CI, без таймеров для определения порядка.
Общий HTTPS-проход проверяет настоящие production routes: обычный вход, смена и восстановление сохраняют совместимость.

## Границы
Этот контроль действует для текущего единственного публичного входа по паролю. Будущие каналы входа,
смена логина, административная замена пароля и обновление auth-библиотеки требуют проверки того же инварианта.
Нельзя включать кеш сессий без отдельной проверки немедленного отзыва.
Если БД недоступна после создания сеанса, cookie не выдаётся; возможна невыданная запись сессии до её истечения.
Сеансы на момент HTTP-ответа могут уже быть отозваны параллельным reset: следующий запрос вернёт 401.
Интерфейс не изменён. Ручная приёмка ранее добавленных экранов остаётся открытой.
