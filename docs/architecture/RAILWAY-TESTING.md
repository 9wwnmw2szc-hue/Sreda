13 сентября пользователь выбрал Railway для тестирования, с последующим переносом готового проекта
на российский сервер. Это заменяет ожидание Яндекса как условие первого тестового запуска.
Подключение Railway к текущему чату пока не подтверждено; инфраструктура не создана.

## Подготовленная конфигурация
Репозиторий 9wwnmw2szc-hue/Biznesoty, ветка codex/railway-testing продолжает PIN-этап.
Не использовать main для этого теста: там ещё нет цепочки последних Draft PR.
Корень сборки — корень репозитория, существующий Dockerfile, данные — PostgreSQL.

| Сервис | Файл Railway Config | Назначение |
|---|---|---|
| web | /deploy/railway/web.json | Сайт/API, миграции перед запуском, /api/health |
| worker | /deploy/railway/worker.json | Один обработчик очереди Telegram, без публичного домена |
| PostgreSQL | Сервис базы с постоянным volume | Общая база для web и worker |

Оба pre-deploy запускают один идемпотентный migration runner; advisory lock сериализует миграции.
Секреты передаются только через Variables Railway, не через код или чат.
APP_URL — точный HTTPS origin тестового домена без завершающего слеша.
BETTER_AUTH_SECRET — одна случайная строка минимум 32 символа, общая для web/worker.
DATABASE_URL — ссылка на приватную строку подключения выбранного PostgreSQL.
NODE_ENV=production; NEXT_PUBLIC_DATA_SOURCE=api уже установлен в Dockerfile.
Next start читает PORT из среды; публичный домен должен вести на этот порт.

## Порядок первого запуска
1. После подключения аккаунта проверить доступные проекты, тариф и ресурсы; использовать отдельное
   тестовое окружение, не изменяя существующие приложения пользователя.
2. Создать PostgreSQL и web, назначить конфигурацию и тестовый домен. Запускать проверенный commit.
3. Первый web-запуск: TELEGRAM_WEBHOOKS_ENABLED=false, worker ещё не запускать.
   Проверить миграции, healthcheck, регистрацию, PIN и восстановление на тестовом аккаунте.
4. Для Telegram создать worker с TELEGRAM_WEBHOOKS_ENABLED=true и теми же APP_URL/БД/секретом.
   После появления heartbeat включить TELEGRAM_WEBHOOKS_ENABLED=true у web и повторно проверить health.
5. В интерфейсе подключить отдельного тестового бота и запустить приём заявок. Проверить реальную
   переписку, единственную заявку, /cancel, перезапуск worker. Токен не записывать в репозиторий.

Автоматический redeploy worker с перекрытием старого и нового процесса требует отдельной приёмки:
текущий heartbeat рассчитан на один worker. Во время тестового обновления сначала выключать
Telegram у web, останавливать старый worker, затем запускать новый и включать Telegram у web.
Автодеплой worker до этой проверки отключить. Сайт и worker закреплять на одном проверенном SHA.

## Приёмка и перенос
До первого запуска использовать только вымышленные клиентские данные. Зафиксировать тестовый URL,
Railway project/service IDs, deployed SHA и результаты проверки после реального развёртывания.
Сейчас этих значений нет; подготовка JSON не подтверждает успешное размещение.

При переносе остановить приём новых заявок и очередь, сделать pg_dump и восстановить PostgreSQL
на целевом сервере, перенести тот же секрет защищённым способом (он нужен токенам ботов и PIN),
проверить аккаунты/заявки и повторно зарегистрировать webhook с новым HTTPS origin.
Переключать домен после проверки; старое окружение выключить после подтверждения переноса.
Подготовленный Dockerfile и SQL не привязаны к Railway; конфигурация Яндекса остаётся в deploy/.
