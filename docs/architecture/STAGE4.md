# Этап 4 — аккаунты и рабочие пространства

## Реализовано
- Вход и автоматическая регистрация после подтверждения email: Better Auth 1.7.4, email OTP, 6 цифр, 5 минут, 5 неверных попыток.
- Серверные сессии на 7 дней. Cookie HttpOnly/SameSite=Lax, Secure при HTTPS; production требует HTTPS. Cookie-cache отключён.
- PostgreSQL, Kysely, проверенные SQL-миграции и отдельная команда запуска миграций. Повторное применение безопасно, checksum защищает уже применённые файлы.
- Создание бизнеса с часовым поясом и owner в одной транзакции. Лимит первой версии — 20 бизнесов на владельца.
- Создание идемпотентно по пользователю и ключу запроса, с advisory lock на аккаунт. Изменённое тело с тем же ключом даёт 409.
- API списка бизнесов и отдельного бизнеса фильтрует активное членство. Чужие и отсутствующие ID дают одинаковый 404.
- Роли owner/admin/operator, проверка разрешений сервисом; UI приглашений и изменения ролей не реализованы.
- Новые страницы входа, первого бизнеса, настроек и добавления бизнеса. Выбранный бизнес — отдельное предпочтение аккаунта.
- При выходе серверная сессия удаляется, клиент очищает ключи sreda и выполняет полную навигацию. Возврат страницы из bfcache требует перезагрузки.

## Реальные маршруты
| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/email-otp/send-verification-otp | Отправить код; 202 при успехе, email нормализуется |
| POST | /api/auth/sign-in/email-otp | Подтвердить email/otp; установить cookie |
| POST | /api/auth/sign-out | Отозвать сессию |
| GET | /api/v1/me | Только id/name/email, без токена |
| GET/POST | /api/v1/businesses | Доступные бизнесы / создание |
| GET | /api/v1/businesses/:id | Бизнес при активном членстве |

Auth-обработчик разрешает только эти три POST-пути библиотеки и удаляет token из тела успешного ответа.
Нативные reset-password, update-user, get-session и прочие auth-маршруты не опубликованы.
Мутации требуют точного Origin и JSON. Ограничение тела — 4096 байт. Ошибки не содержат stack, запросы БД, email или секреты.
Общий и per-email лимиты атомарны в PostgreSQL. Отправка: 1/мин и 5/час на email; проверка: 10/10 минут плюс лимит попыток самого OTP.
Это не заменяет edge-защиту от распределённого злоупотребления перед публичным запуском.

## Запуск на согласованном окружении
1. Node.js 22.18+; npm ci.
2. Создать отдельную PostgreSQL-базу и заполнить .env.local по .env.example.
3. APP_URL — один origin без завершающего slash; в production только HTTPS.
4. BETTER_AUTH_SECRET — случайный секрет от 32 байт. DATABASE_URL и SMTP-пароль только на сервере.
5. npm run db:migrate (отдельный шаг, до запуска приложения; не из web-запроса).
6. SMTP_HOST/USER/PASSWORD/FROM, порт 465 либо 587; TLS обязателен.
7. npm run build; npm start.

Миграции требуют DDL-доступа; runtime-пользователю нужны только необходимые DML-права. В миграциях нет тестовых аккаунтов.
Нельзя использовать production-базу для TEST_DATABASE_URL: это изолированная пустая тестовая БД.
После выбора инфраструктуры добавить регламент очистки истёкших verification/session/request_limit, резервного копирования и восстановления.

## Режимы данных
Обычный режим api требует реального входа. При отсутствии настроек нет mock fallback: пользователь видит недоступность входа.
Явный NEXT_PUBLIC_DATA_SOURCE=mock действует только в development. Production игнорирует его.
Mock-заявки, посты, подписки и подключения в api-режиме не показываются. Эти модули ещё не реализованы, поэтому списки пустые.
Каталог — пока статическая спецификация четырёх решений с предварительными ценами.
Мастер приёма заявок в api-режиме — предпросмотр в памяти вкладки, без сохранения и реальных событий. Серверные черновики — этап 5.

## Проверки и границы
- Локальные интеграционные тесты используют настоящий SQL PostgreSQL через PGlite и тот же auth/application/workspace код; исходящие письма перехвачены тестовым отправителем. Это не проверка реального SMTP.
- Проверены вход, неверный/истёкший/повторный код, лимиты, отзыв/истечение сессии, CSRF, валидация, атомарность создания, owner constraint, два пользователя и отзыв членства.
- Конкурентное создание и одновременная проверка OTP требуют отдельных PostgreSQL-соединений; для них добавлен CI с PostgreSQL 17. Результат CI нужно проверить по head PR, а не выводить из локальных тестов.
- Нативный PostgreSQL в текущем контейнере не удалось запустить из-за недоступности непривилегированного UID. PGlite не выдаётся за проверку многопроцессной конкуренции.
- Экраны входа и создания бизнеса проверяются на 1440/1280/900/390; создание бизнеса визуально проверено на временной UI-fixture без доступа к реальным аккаунтам. Fixture удалена из поставки.
- Browser login с реальной почтой, настройка провайдера, реальные пользователи и production не выполнялись. Этап подготовлен как код для review; запуск на реальной инфраструктуре — отдельная проверка.
