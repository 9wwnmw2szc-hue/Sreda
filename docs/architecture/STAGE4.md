# Этап 4 — аккаунты и рабочие пространства

## Реализовано
Регистрация `/register`: логин, пароль, повтор пароля. Вход `/login`: логин/пароль. Better Auth 1.7.4 username plugin, стандартное хеширование паролей, signed HttpOnly SameSite=Lax cookies, Secure на HTTPS, 7 дней. Сервер проверяет совпадение паролей, длину 10–128, уникальный нормализованный логин 3–30 символов. Регистрация сразу создаёт сессию.

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/sign-up/username | username/password/passwordConfirmation; создать аккаунт |
| POST | /api/auth/sign-in/username | username/password; войти |
| POST | /api/auth/sign-out | Отозвать сессию |
| GET | /api/v1/me | id/name/username, без email и токена |
| GET/POST | /api/v1/businesses | Список доступных / создание с Idempotency-Key |
| GET | /api/v1/businesses/:id | Доступ только активному участнику |

Мутации требуют точный Origin и JSON до 4096 байт. У регистрации/входа отдельные HMAC-ключи лимитов: 10 попыток/10 минут на логин и общий 300/мин. Дополнительные лимиты библиотеки 100/мин. Перед публичным запуском настроить доверенный reverse proxy и edge-защиту. Не доверяем произвольным forwarded IP.

Business и owner создаются транзакционно; идемпотентность и advisory lock защищают от повторов. Чужой и неизвестный бизнес дают одинаковый 404. Роли проверяются сервером. Реальные режимы не подставляют demo-заявки или подписки. Черновики приёма заявок в реальном режиме пока только в памяти.

## Запуск
1. `npm ci`.
2. Скопировать `.env.example` в `.env.local`, настроить PostgreSQL DATABASE_URL, APP_URL (HTTPS для production) и случайный BETTER_AUTH_SECRET не короче 32 байт. SMTP больше не нужен.
3. `npm run db:migrate` — применить 001/002/003. Старые миграции не изменяются.
4. `npm run build`, `npm start`. Разработка: `npm run dev`.

Технический .invalid email нужен внутренней схеме Better Auth; он не является почтой пользователя. Публичные email/OTP API запрещены. Старые тестовые email-аккаунты не конвертируются автоматически (см. A13).

## Проверки и границы
`npm test`, lint, build, typecheck. Тесты проверяют регистрацию, совпадение паролей, хеширование, повтор логина, вход с другим регистром, лимиты, cookies, logout/expiry, CSRF и tenant isolation. Локально PGlite; concurrency — PostgreSQL 17 в CI.

Вход по коду Telegram/VK пока не реализован: в настройках показано условие подключения бота и подтверждения личного получателя. Нет реальных интеграций, доставки кодов, восстановления пароля, размещения и production. Прежние скриншоты email-входа исторические.

Следующий шаг: review и проверка регистрации → создание бизнеса → переключение → выход на согласованном окружении. Затем серверные заявки. Telegram/VK отдельно, согласно A14.
