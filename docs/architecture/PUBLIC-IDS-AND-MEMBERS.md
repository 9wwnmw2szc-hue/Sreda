# Публичные ID, внутренние связи и участники бизнеса

Статус: архитектурное решение для согласования, 11 сентября 2026.

## Цель

Сохранить единое ядро данных для сайта, Telegram и VK, не раскрывать внутренние ключи базы и дать владельцу безопасный способ пригласить второго администратора.

## Короткое решение

Используем два идентификатора для аккаунта и бизнеса:

- внутренний UUID — только база и сервер;
- публичный непрогнозируемый ID — сайт, приглашения и поддержка.

Публичный ID не кодирует данные и не содержит токены. Все заявки, клиенты, подключения и заказы внутри базы ссылаются на внутренний `business_id`. Сервер сначала проверяет публичный ID и членство пользователя, затем работает с внутренним UUID.

## Плюсы

- Внешний пользователь не видит последовательные ключи и структуру базы.
- Telegram, VK и Web работают с одной бизнес-сущностью и не расходятся по данным.
- Можно безопасно показывать ID в настройках и использовать его в приглашениях.
- Замена внутренних UUID или перенос базы не меняет публичные ссылки.
- Права доступа проверяются централизованно через `business_member`.
- Повторная доставка события из канала дедуплицируется по бизнесу, каналу и внешнему ID события.
- Поддержка может найти бизнес по публичному ID, не получая токены.

## Минусы и стоимость

- Появляется дополнительное сопоставление public ID → internal UUID.
- Нужно не забыть проверку членства на каждом endpoint, а не только при открытии страницы.
- Приглашение администратора требует отдельного состояния `pending/accepted/revoked/expired`.
- Нужны миграции существующих записей и тесты доступа между бизнесами.
- Публичный ID сам по себе не является секретом: его можно передать другому человеку. Он только идентифицирует объект, но не даёт доступ.
- Для восстановления пароля и входа по коду нужны отдельные подтверждённые каналы; ID не должен использоваться как единственный фактор.

## Модель данных

### Аккаунт

`user.id` — закрытый UUID. `user.public_id` — уникальный случайный идентификатор вида `usr_...`, показываемый владельцу.

### Бизнес

`business.id` — закрытый UUID. `business.public_id` — уникальный случайный идентификатор вида `biz_...`.

### Членство

`business_member` связывает внутренние `business_id` и `user_id`, хранит роль, статус и дату добавления. Публичные ID не используются как внешние ключи внутри базы.

### Подключения

Отдельная запись подключения хранит `business_id`, `platform`, внешний Telegram/VK ID, имя и статус. Один бизнес может иметь несколько каналов.

### Секреты

Токены не находятся внутри ID и не хранятся в открытом виде в бизнесе или подключении. Они лежат в отдельной таблице/секретном хранилище в зашифрованном виде с версией ключа. API, логи и клиент их не возвращают.

## Добавление администратора

1. Владелец вводит `usr_...` второго пользователя.
2. Сервер нормализует и проверяет формат публичного ID.
3. Создаётся приглашение с выбранной ролью и сроком действия.
4. Приглашённый пользователь принимает приглашение после входа в свой аккаунт.
5. Сервер транзакционно создаёт активное членство.
6. Владелец может отозвать приглашение или членство; отзыв действует на следующий запрос.

Знание `usr_...` не даёт доступа. Нельзя автоматически активировать администратора только по введённому ID: это позволило бы ошибочно или злоумышленно добавить чужой аккаунт.

## Роли первого релиза

| Роль | Доступ |
|---|---|
| Владелец | Всё, участники, подключения, оплата, удаление/архивирование бизнеса |
| Администратор | Настройки бизнеса, решения, заявки, клиенты; без передачи владения и просмотра секретов |
| Оператор | Просмотр и обработка заявок/клиентов; без подключений, оплаты и управления участниками |

Позже разрешения можно расширить отдельными capability (`leads.read`, `leads.manage`, `connections.manage`, `billing.manage`). До этого не вводим произвольный конструктор прав: он усложнит продукт и увеличит риск ошибок.

## Единое ядро каналов

Канальные адаптеры переводят Telegram/VK/Web-события в общую модель:

```text
внешнее событие → адаптер → нормализация → business_id → общая заявка/клиент/заказ
```

Внешние ID никогда не становятся внутренними ID и не заменяют их. Для каждого события сохраняем `source` и `external_event_id`; уникальность ограничена конкретным бизнесом и каналом.

## Основные ошибки, которые предотвращаем

- Не использовать последовательные публичные номера.
- Не принимать `businessId` из тела запроса как доказательство доступа.
- Не искать участника только по публичному ID без проверки текущей сессии.
- Не выдавать токены администраторам и операторам.
- Не дублировать бизнес-логику в Telegram, VK и Web.
- Не давать доступ до принятия приглашения.
- Не удалять данные при отзыве участника: менять статус и сохранять аудит.

## План внедрения

1. Добавить `public_id` и уникальные ограничения для `user` и `business`.
2. Перевести API и клиент на публичные ID; внутренние UUID убрать из ответов.
3. Добавить таблицу подключений и отдельное зашифрованное хранилище секретов.
4. Добавить приглашения участников и аудит действий.
5. Подключить Telegram-адаптер, затем VK-адаптер к общему ядру.
6. Добавить вход по коду только после подтверждения личной админ-панели бота.

Каждый пункт выполняется отдельным этапом с миграцией, серверными тестами tenant isolation, тестами ролей, повторных событий и проверкой UI на всех разрешениях.

## Acceptance criteria

- Внешний API никогда не отдаёт внутренние UUID, токены или секретные поля.
- Пользователь видит и может использовать только `usr_...` и `biz_...`.
- Чужой или неизвестный бизнес отвечает одинаковым 404.
- Знание публичного ID не открывает доступ.
- Приглашение требует принятия и повторно не активируется после отзыва/истечения.
- Telegram, VK и Web создают записи в одной бизнес-сущности.
- Дублирующее внешнее событие не создаёт вторую заявку.
- Отзыв участника блокирует следующий запрос без удаления исторических данных.
